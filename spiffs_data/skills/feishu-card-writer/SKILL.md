# 飞书卡片写作器

当回复会发送到飞书时，按“飞书 2.0 卡片 + markdown 组件”的展示特点来组织内容，让结果更适合手机和桌面阅读。

## 何时使用

- 当前对话通道是飞书
- 用户明确说“发到飞书”“适合飞书阅读”“做成飞书格式”
- 输出是总结、分析、提醒、工具结果、操作说明这类结构化内容

## 核心原则

1. 先给结论，再给细节
2. 优先短段落、列表、小节，不要一上来堆大段文字
3. 最多使用两级标题，避免层级过深
4. 能用列表就不用表格；表格只在信息天然是对照关系时才使用
5. 代码块只保留必要片段，不要粘贴大段源码
6. 每一段尽量短，适合在飞书客户端直接扫读
7. 避免“为了方便理解我将从以下几个方面展开”这类套话

## 推荐格式

优先使用这种顺序：

1. 一句话结论
2. 2-6 个要点
3. 如果需要，再补“下一步建议”或“注意事项”

示例结构：

```md
# 结论

一句话说清楚结果。

## 关键点

- 要点 1
- 要点 2
- 要点 3

## 下一步

- 建议动作 1
- 建议动作 2
```

## 不推荐的写法

- 很长的开场白
- 超过两级的标题嵌套
- 大而宽的 Markdown 表格
- 超长代码块
- 一整段没有换行的技术说明

## 表格使用建议

- 只有在“字段 / 说明”“模块 / 职责”“方案 / 对比”这类天然对照信息中才使用表格
- 表格尽量控制在 2-3 列
- 行数尽量少；如果内容很多，改成列表更稳

## 代码与命令展示建议

- 只贴最关键的命令或最小代码片段
- 命令优先单行展示
- 如果代码超过十几行，优先总结关键点，而不是整段贴出

## 常见场景模板

### 1. 工具执行结果

```md
# 已处理

一句话说明执行结果。

## 结果

- 做了什么
- 成功还是失败
- 关键输出是什么

## 下一步

- 用户现在可以做什么
```

### 2. 代码分析

```md
# 项目分析

一句话概括项目定位。

## 核心模块

- 模块 A：作用
- 模块 B：作用
- 模块 C：作用

## 启动流程

1. 步骤 1
2. 步骤 2
3. 步骤 3

## 结论

- 最值得关注的点 1
- 最值得关注的点 2
```

### 3. 提醒 / 通知

```md
# 提醒

一句话说明发生了什么。

## 你可以做的事

- 动作 1
- 动作 2
```

## 与代码分工

- 代码层只负责稳定的卡片外壳：统一用飞书 JSON 2.0 interactive card 发送
- 卡片标题、模板配色等不要依赖代码里的内容猜测；正文结构、语气、层次主要由你来控制
- 不要假设系统会从第一句话自动提取标题；需要标题时，直接在正文 markdown 里自己写

## 注意事项

- 飞书已经统一走 2.0 interactive card，正文由 markdown 组件渲染
- 因此可以使用标准 Markdown，但要优先考虑阅读体验，而不是追求文档排版炫技
- 如果内容特别长，优先“摘要 + 要点”，避免一次展开过多细节
